# Candidate Take-Home API

## Problem Statement

The Frontend Engineer take-home assessment requires a dependable API that candidates can run a local frontend against. The repository currently contains requirements but no API service or unified, frontend-ready contract. The team needs to settle behavior before backend implementation begins.

## Solution

Build a Go API for assessment exercises A1, A2, and A3. Provide a stable REST and WebSocket contract, enforce candidate-tenant isolation on every operation, and supply candidate-ready documentation, test accounts, seed data, and a reset procedure. REST endpoints, payload expectations, validation, and WebSocket events are defined below.

## User Stories

1. As an assessment operator, I want to provision one isolated candidate tenant with an Admin login and an Employee login, so that candidates can test both roles without seeing one another's data.
2. As an Admin, I want to sign in and refresh my session securely, so that I can use the API throughout the assessment.
3. As an Admin, I want to create an Employee with a login account, so that the Employee can sign in from another browser session.
4. As an Admin, I want to list, search, filter, sort, inspect, update, and deactivate Employees, so that I can demonstrate the A1 management workflow.
5. As an Employee, I want to read my own profile and update my name, phone, and avatar, so that I can manage my personal details without changing privileged fields.
6. As an assessment operator, I want to seed department and task lookup values, so that frontend forms have usable choices immediately.
7. As an Admin, I want to upload and display an Employee avatar through private storage, so that files remain inaccessible without API authorization.
8. As an Admin, I want to submit a Project with nested Phases and Tasks in one request, so that the A3 dynamic form has a complete persistence path.
9. As an Admin, I want validation errors for every invalid nested field in one response, so that the frontend can show errors beside the correct inputs.
10. As an authenticated user, I want to retrieve tenant Projects and all nested records, so that I can verify what the form saved.
11. As an Employee, I want a conversation with my owning Admin created automatically, so that I can start chatting as soon as my account exists.
12. As an Admin, I want an inbox of my tenant's Employee conversations with last-message and unread information, so that I can find and respond to candidates.
13. As a conversation participant, I want to send and retry messages without duplicates, so that transient network failures do not lose or duplicate messages.
14. As a conversation participant, I want to load older messages and synchronize newer messages after reconnecting, so that the conversation remains complete and ordered.
15. As a conversation participant, I want live message, delivery, read, typing, and presence updates across my sessions, so that chat behaves consistently in multiple browsers.
16. As a candidate, I want consistent response envelopes, validation details, request IDs, pagination, and conflict behavior, so that I can integrate against predictable API behavior.
17. As an assessment operator, I want to reset a candidate tenant between assessments, so that the next candidate starts with clean assessment data and revoked sessions.
18. As a candidate, I want complete REST and WebSocket documentation plus working test accounts, so that I can build and verify the frontend without guessing the API contract.

## Implementation Decisions

- **Service and storage:** Initialize this existing repository with `bkgo init` (no nested project directory), then run `go mod tidy`. Generate each domain module with `bkgo generate module`; keep domain entities and ports, use cases, Fiber handlers, and repository adapters in their generated hexagonal layers. Extend generated use-case tests. Construct database, JWT, and object-storage adapters only at the composition root, behind `bkgo/contract` ports and the matching `*_ENABLED` configuration. Use PostgreSQL through a `bkgo` database adapter. Store files in a private self-hosted RustFS bucket. Keep credentials server-side, validate uploads in the API, authorize before issuing short-lived presigned download URLs, and never expose public bucket access.
- **Tenant and identity:** An operator provisions one candidate tenant per candidate with one Admin and one login-enabled Employee account. The API does not create or modify Admin accounts and does not accept a tenant selector. Authentication determines the tenant. Login email is globally unique because login uses email and password without tenant selection. Admins manage Employees and tenant records only in their tenant. Employees read only their own profile and update only `fullName` and `phone`. Avatar changes use the avatar upload endpoint. Tenant ownership checks apply in addition to role checks; every route declares allowed roles through Go-native route/middleware conventions. Employee deletion disables login while retaining the Employee record and chat history. Creating an Employee with the email of a Deleted Employee in the same tenant restores that Employee; another tenant's email stays reserved. Each tenant supports at most 200 login-enabled Employees.
- **Shared HTTP contract:** Use `/api/v1`, UTF-8 JSON, `camelCase` fields, opaque string IDs, and UTC ISO 8601 timestamps. Single results use `{ "data": result }`; paginated results use `{ "data": [...], "meta": ... }`; empty success uses `{ "data": null }`. Every response includes `X-Request-Id`; generate one if absent. Errors use `{ "error": { "code", "message", "details" }, "requestId" }`. Malformed requests return `400`; authentication `401`; authorization `403`; inaccessible resources `404`; duplicates, stale versions, or conflicting idempotency keys `409`; validation `422`; rate limits `429` with `Retry-After`; unexpected failures `500`. Validation reports every error with the complete field path. General rate limit is at least 100 requests per minute per user; login and refresh have stricter limits. See the OWASP-aligned security baseline in `API_SPEC.md`.
- **Authentication:** `POST /auth/login` accepts email/password and returns bearer access and refresh tokens plus the authenticated user. Invalid credentials return a generic `401`. Access tokens last 30 minutes. Refresh tokens last 7 days, rotate on use, and cannot be reused after rotation/revocation. `POST /auth/refresh` rotates the pair. Login, refresh, and `GET /auth/me` return the authenticated user, including `employeeId` (`null` for an Admin). Each access token is bound to an active session; logout immediately revokes that session, while account disablement and tenant reset revoke all affected sessions. Production requires PostgreSQL and JWT authentication with a strong signing secret. No endpoint creates or edits an Admin.
- **Employee operations:** `GET /employees` is Admin-only and supports page/limit, name/email/code search, department and status filters, and deterministic sorting by name, hire date, or creation time. `GET /employees/{id}` allows Admins within their tenant and the Employee themself. Admin-only `POST /employees` creates an Employee login and the Employee's one-to-one conversation atomically; password is required and at least 8 characters. `PATCH /employees/{id}` requires the current `version`; Admins may update Employee profile/administrative fields, while Employees may update only their name and phone. Stale versions return `409`. Admin-only `DELETE /employees/{id}` disables login but preserves records and chat history. `POST /employees` with that Employee's email in the same tenant restores the same `id` and code, keeps the avatar and `createdAt`, increments `version`, replaces the password, and returns `201`. `GET /departments` returns shared departments. `POST /employees/{id}/avatar` accepts JPG, PNG, or WebP up to 2 MB from an Admin or the Employee themself. Email is valid and globally unique; name is 2–100 characters; department must exist; hire date cannot be in the future.
- **Project operations:** A3 uses Project → Phase → Task. Authenticated Admin-only `POST /projects` creates the whole hierarchy in one transaction. `GET /projects` lists only tenant Projects with page/limit and optional search; `GET /projects/{id}` returns the complete hierarchy; Admin-only `DELETE /projects/{id}` supports assessment cleanup. Authenticated `GET /lookups/task-types` returns `feature` and `bug`; `GET /lookups/priorities` returns `low`, `medium`, `high`, and `critical`. `ownerId` and `assigneeId` must identify active Employees in the authenticated tenant. Project codes are unique within the tenant. Dates are inclusive `YYYY-MM-DD`; Phases fit within Project dates and Task due dates fit within Phase dates. A Project has 1–20 Phases, each Phase has 1–100 Tasks, and one request supports at least 500 Tasks. Bug Tasks require severity `minor`, `major`, or `critical`; other Task types require `severity: null`. Validate every field and return full paths such as `phases[0].tasks[1].severity`. `Idempotency-Key` with the same payload returns the original result; reuse with a different payload returns `409`.
- **Chat REST:** Each Employee has exactly one conversation with the Admin who owns the Employee; it is created with the Employee. `GET /chat/conversations` returns the Admin's tenant inbox or the Employee's own conversation, supports search/unread filtering and page/limit, and sorts the Admin inbox by recent update. `POST /chat/conversations` for an Employee returns that Employee's existing conversation. Participants can `GET /chat/conversations/{id}`, read messages from `GET /chat/conversations/{id}/messages`, send via `POST /chat/conversations/{id}/messages`, and mark read via `POST /chat/conversations/{id}/read`. `GET /chat/unread-count` returns the caller's aggregate count. Message text is plain text, 1–2,000 characters. Message send requires `clientMessageId`; retrying the same ID/payload returns the original message, while reusing the ID with a different payload returns `409`.
- **Chat ordering and state:** The server assigns a stable increasing sequence per conversation; order does not depend on message ID. Message cursors `before` and `after` are exclusive; results are oldest-to-newest. `after` returns all later messages for reconnect synchronization. `sent` means persisted; `delivered` means at least one recipient session acknowledged receipt; `read` means the recipient marked it seen. Delivery and read positions are shared across the participant's sessions and advance monotonically. Unread counts include only messages from the other participant.
- **WebSocket:** An authenticated client gets a one-use ticket valid 30–60 seconds from `POST /chat/ws-ticket`, then connects to `wss://<host>/ws/chat?ticket=<ticket>`. Never place access tokens in URLs. The server validates Origin and tenant/participant access. Events use `{ "type", "data", "ts" }`. Client events are `message.delivered` (through last contiguous message), `message.read` (through last displayed message), temporary `typing`, and optional `ping`. Server events are `message.new`, `message.status`, `conversation.updated`, `unread.updated`, `typing`, `presence`, and `error`. Broadcast chat events to all authenticated sessions of both participants. Presence is online while at least one authenticated chat session is active; typing and presence are temporary, not persisted. Server pings about every 25 seconds and clients respond with pong. Message creation remains REST-based; REST `/read` is the read-ack fallback.
- **Pagination and CORS:** Non-chat lists default to `page=1`, `limit=20`, with a maximum limit of 100 and deterministic sorting. Chat message pages default to 30 and cap at 100. CORS allows `http://localhost:3000` and `http://localhost:5173` and headers `Authorization`, `Content-Type`, and `Idempotency-Key`; WebSocket checks the same allowed Origins.
- **Candidate readiness and deployment boundary:** Provision at least two isolated test tenants, each with Admin and Employee logins; seed at least five shared departments plus Task lookups. Optional sample Employees used for list testing have no login accounts. An operator-only reset revokes tenant sessions and removes tenant Employees, conversations, and Projects before reuse; it is not a candidate API endpoint. Test credentials are separate from production credentials and are shared outside the API. Publish REST documentation through OpenAPI/Swagger or Postman and document every WebSocket event. The API must be reachable over HTTPS/WSS. The API owner supplies ArgoCD registration, database instance selection, ingress, hostname, and TLS details.

## Testing Decisions

- Test externally visible HTTP and WebSocket behavior at one integration seam, using PostgreSQL and a private RustFS test bucket. Do not assert handler internals or storage implementation details.
- Cover authentication and refresh-token rotation; role and tenant isolation; Employee create/login/update/deactivation; avatar upload authorization; Project validation, 500-Task atomic writes, and idempotency; message retry deduplication, cursor ordering, acknowledgements, unread counts, reconnect sync, and multi-session events; and candidate tenant reset.
- Verify end-to-end candidate flows: Admin creates an Employee, the Employee signs in and chats with that Admin; Admin submits a nested Project and retrieves the saved hierarchy; a second tenant cannot read or mutate the first tenant's resources.
- Exercise the authentication/tenant boundary, Employee directory/profile/account lifecycle, private avatar storage, Project hierarchy operations, chat REST, chat WebSocket delivery, and operator reset behavior.
- The current repository has no API implementation or test suite to reuse. Test fixtures and integration setup will be introduced with the service implementation.

## Out of Scope

- Building the candidate frontend.
- Candidate-facing Admin creation or tenant selection.
- Employee-to-Employee chat, chat attachments, and optional simulated latency/errors.
- Deployment platform implementation details owned by the API owner, including ArgoCD registration, replica count, database instance selection, ingress, hostname, and TLS configuration.
- API features not listed in the implementation contract above.

## Further Notes

- Source requirements: the backend requirements document and the Frontend Engineer take-home assessment.
- Use the domain vocabulary already established for Candidate tenant, Admin, Employee, Project, Phase, Task, Conversation, and Message.
- The route to this spec is tracked by [Plan the candidate take-home API contract](https://github.com/aifgrouplaos/candidate-api/issues/1).
- Local frontend origins are explicitly limited to ports 3000 and 5173. The deployment owner must provide the public API base URL and test credentials separately.
